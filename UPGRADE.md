# Home Center 0.56.0 — обновление и откат

Обновление выполняется только на официальный квалифицированный Stable-релиз. Перед изменениями проверьте текущую версию, release identity, целостность артефактов, резервную копию и возможность отката.

## Важное ограничение текущего Stable 0.56.0

У выпуска 0.56.0 опубликованы runtime-архив, отдельный `.sha256`, `SHA256SUMS`, SBOM, acceptance record и release manifest. Однако сам runtime-архив v0.56.0 был опубликован **до** исправления archive-shape контракта, который требует fail-closed node-updater. Поэтому наличие checksum-sidecar не означает, что опубликованный runtime-архив 0.56.0 можно безопасно подавать в canonical `install-node.sh`/auto-update путь.

Исправленный publication contract уже находится в Stable-ветке и применяется к **последующим** квалифицированным релизам. Опубликованный v0.56.0 задним числом не изменяется. До выхода следующего Stable с новым runtime contract используйте только явно подтверждённый для вашей исходной версии install/upgrade путь; не обходите fail-closed проверки вручную.

## Перед обновлением

1. Зафиксируйте текущую версию, revision, путь `/opt/home-center/current` и состояние сервисов.
2. Создайте проверяемую резервную копию state DB, конфигурации и необходимых пользовательских данных.
3. Определите целевую версию и убедитесь, что она действительно имеет статус Public Stable, а не RC/Draft/source-only кандидат.
4. Для целевого релиза проверьте SHA-256, `SHA256SUMS`, release identity, SPDX SBOM, acceptance record и release manifest.
5. Убедитесь, что именно этот релиз поддерживает используемый update path. Для canonical node-updater runtime-архив должен соответствовать его обязательной archive shape; checksum сам по себе недостаточен.
6. Сохраните предыдущий версионированный release-каталог и recovery point до завершения post-update acceptance.

## Canonical node-updater для совместимых последующих Stable

`deploy/scripts/install-node.sh` является fail-closed узловым deployment-путём. Он требует точный artifact SHA-256, hostname/node identity, transaction id и точные expected current release/version/revision. Перед переключением он проверяет архив, текущее release identity и блокировку параллельной mutation, сохраняет rollback point/state DB, а при неуспешном запуске сервиса выполняет автоматический rollback.

Не ослабляйте эти preconditions и не подменяйте несовместимый runtime-архив ручной распаковкой в `/opt/home-center/current`.

## Multi-node / двухузловой профиль

Обновляйте узлы последовательно, сохраняя single-writer и доступность фактически поддерживаемого профиля. Для штатного двухузлового тестового профиля сначала обновляется **второй узел**, затем после проверки health, межузловой связности, репликации/согласованности состояния и сервисов — **первый узел**. Если первый обновляемый узел не прошёл проверки, переходить к следующему нельзя.

Автоматический failover разрешается только для профиля, где он отдельно поддержан и подтверждён fencing/recovery-процедурой.

## Проверки после каждого узла

Проверьте запуск сервисов, release identity, TLS, readiness/health, Web-доступ, peer health, согласованность/репликацию состояния, сохранность локального admin/session/audit state, backup readiness и отсутствие критических ошибок. Не считайте обновление успешным только по факту запуска процесса.

## Откат

При неуспехе немедленно остановите дальнейшее обновление. Используйте rollback point, созданный штатным deployment-путём, либо предыдущий проверенный версионированный release-каталог. После отката повторно проверьте сервисы, release identity, health, state DB, конфигурацию, admin/session/audit state и peer consistency.

При несовместимом изменении данных используйте восстановление из проверенной резервной копии согласно документации конкретного выпуска; не выполняйте неподтверждённый ручной downgrade хранилища.

Обновление не должно сбрасывать пользовательские настройки, данные и установленный административный пароль.
